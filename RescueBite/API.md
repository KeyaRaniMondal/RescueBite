# RescueBite API Reference

Complete HTTP API documentation for the RescueBite backend (Express 5 + Prisma 7 + PostgreSQL).
Generated by reading the source under `src/` — every field name, message string and status code below matches the implementation.

- **Base path:** `/api/v1`
- **Default local origin:** `http://localhost:5000` (`PORT=5000`)
- **Format:** JSON (some endpoints accept `multipart/form-data` and `application/x-www-form-urlencoded`)
- **File map:** routes live in `src/modules/*/**.route.ts`, mounted in `src/app.ts`

## 1. Conventions

### 1.1 Versioning and aliases

All business endpoints are mounted under `/api/v1`. Two routers are mounted on **two prefixes each** — the handlers are identical:

| Router | Mounted at |
| --- | --- |
| Food listings | `/api/v1/food-listing` **and** `/api/v1/food-listings` |
| Reservations | `/api/v1/reservation` **and** `/api/v1/reservations` |

Use the plural forms (they are what the web client uses).

### 1.2 Content types

- Request bodies are parsed globally by `express.urlencoded({ extended: true })` then `express.json()` (100 kB default limit) and `cookie-parser`.
- Send `Content-Type: application/json` unless the endpoint is marked **multipart**.
- On multipart endpoints, text fields arrive as strings; numeric Zod fields that accept strings are marked "coerced" below.
- Sending `multipart/form-data` to a JSON-only endpoint leaves `req.body = {}` → usually a `400` validation error.

### 1.3 Authentication

Protected endpoints accept the access token from **either** source:

```
Authorization: Bearer <accessToken>        # preferred (used by the web client)
Cookie: accessToken=<accessToken>          # httpOnly cookie set at login
```

Token payloads: `{ userId, name, email, role }`, signed with `JWT_ACCESS_SECRET` (expires per `JWT_ACCESS_EXPIRES_IN`, default `1d`) or `JWT_REFRESH_SECRET` (default `7d`).

Failures come straight from the auth middleware and use a **shorter envelope than the rest of the API** (no `statusCode`, no `data`):

| Situation | Status | Body |
| --- | --- | --- |
| No token | `401` | `{"success":false,"message":"Authentication required. No token provided."}` |
| Bad/expired JWT | `401` | `{"success":false,"message":"Invalid or expired token"}` |
| Role not allowed | `403` | `{"success":false,"message":"Forbidden: You do not have permission to access this resource"}` |

### 1.4 Roles

`ADMIN` · `PROVIDER` · `RECEIVER` (see [Enumerations](#2-enumerations)).
Role gates are applied per route via `authenticate` + `authorizeRoles(...)`. **Public** endpoints require no token.

### 1.5 Success envelope

All JSON successes go through `sendResponse` (`src/utils/sendResponse.ts`):

```json
{
  "success": true,
  "statusCode": 200,
  "message": "Human readable message",
  "data": {},
  "meta": { "page": 1, "limit": 10, "total": 42, "totalPages": 5 }
}
```

- `meta` is emitted **only** by the two paginated admin list endpoints; everywhere else the key is absent from the JSON.
- Payment gateway browser callbacks answer with a **302 redirect**, not JSON (see [Payments](#47-payments)).

### 1.6 Error envelope

Errors are handled by the inline global handler in `src/app.ts`:

```json
{
  "success": false,
  "statusCode": 400,
  "message": "Exact error message",
  "data": null
}
```

Status resolution, in order:

1. `AppError(statusCode, message)` → uses its own `statusCode`.
2. Otherwise, **case-sensitive** substring matching on `message`:

   | Message contains | Status |
   | --- | --- |
   | `already exists` | `409` |
   | `Authentication required` | `401` |
   | `Forbidden` | `403` |
   | `not found` | `404` |
   | `A valid` | `400` |
   | `must be` | `400` |
   | *(anything else)* | `500` |

   ⚠️ Some service errors (`Invalid credentials`, `Invalid OTP`, `User is blocked`, …) match no keyword and are therefore returned with **HTTP 500** even though they are client-side conditions. They are listed with their real status in [Error reference](#5-error-reference).

> Note: `src/middlewares/globalErrorHandler.ts` exists but is **not mounted**; the handler in `app.ts` is the one that runs.

### 1.7 Validation

- Body validation uses Zod 4 via `validateRequest(schema)` middleware (auth, user, admin routes) or `schema.safeParse(req.body)` inside the controller (food listing, reservation, provider routes). Behavior is identical.
- Only the **first** issue is surfaced: `400` with `issues[0].message` (fallback `Invalid input`).
- Unknown keys are stripped from `req.body`.
- Query/path params are **not** validated by the shared middleware; a few endpoints validate `req.query` themselves (admin lists, food-listing filters) and return `400` with the first Zod message.

### 1.8 Dates, IDs, pagination

- All timestamps are serialized as **ISO-8601 strings** (`toISOString()`); nullable timestamps are `null`.
- All IDs are UUID strings.
- Only `GET /admin/users` and `GET /admin/providers` paginate: `page` (default `1`), `limit` (default `10`, max `100`), with `meta = { page, limit, total, totalPages }`.

### 4.2 Authentication

Mounted at `/api/v1/auth`. Body validation via Zod unless noted. All flows issue the JWT pair described in [§1.3](#13-authentication).

#### `POST /auth/register`

Access 🔓 · `application/json`

Registers a receiver/provider candidate and emails a 6-digit OTP. **No user row is created yet** — the payload is parked in Redis for 5 minutes.

| Body field | Type | Required | Rules / exact error message |
| --- | --- | --- | --- |
| `name` | string | ✅ | 3–10 chars → `Name must atleast 3 characters long!!!`, `Too big: expected string to have <=10 characters`, type → `Not A String!!!!!` |
| `email` | string (email) | ✅ | → `Not email!!` |
| `password` | string | ✅ | ≥8 chars, lower, upper, digit, special → `Password Must Minimum 8 Characters Long.`, `Password must contain atleast 1 Lowercase Letter`, `…1 Uppercase Letter`, `…1 Number`, `…1 Special Character` |
| `role` | `ADMIN`\|`PROVIDER`\|`RECEIVER` | ⬜ | default `RECEIVER` → `Invalid option: expected one of ADMIN\|PROVIDER\|RECEIVER` |
| `customer.contactNumber` | string | ⬜ | |

Side effects: email is trimmed + lowercased; password hashed with bcrypt (8 rounds); Redis keys `customer registration otp: <email>` and `customer-registration-data:<email>` (TTL 300 s); OTP emailed via `registrationUserOtp.ejs`.

```
201 { "success": true, "statusCode": 201, "message": "Verification OTP sent", "data": null }
```

Errors: `400` validation · `409` `User with this email already exists` · `500` SMTP/Redis failures.

#### `POST /auth/verify-email`

Access 🔓 · `application/json` — confirms the OTP, creates the user, logs in.

| Body field | Type | Required | Rules |
| --- | --- | --- | --- |
| `email` | string (email) | ✅ | → `Not email!!` |
| `otp` | string, exactly 6 chars | ✅ | → `Too small: expected string to have exactly 6 characters` |

```
200 {
  "success": true, "statusCode": 200, "message": "User logged in successfully",
  "data": { "accessToken": "…", "refreshToken": "…" }
}
```

Also sets cookies `accessToken` (24 h) and `refreshToken` (7 d) — `httpOnly`, `secure: false`, `sameSite: none`, `path: /`.

Side effects: creates `User` (`status: ACTIVE`, `emailVerified: true`, role from payload or `RECEIVER`) plus a `Customer` row when role is `RECEIVER`; password omitted from any output; welcome email sent.

Errors: `400` validation · `404` `User not found` · `500` `User is Blocked` · `500` `Email ALready Verified` · `500` `User is Deleted` · `500` `Invalid OTP` · `500` `OTP Does Not Match` · `500` `customer Doesnt Exist` (OTP/payload expired after 5 minutes).

#### `POST /auth/login`

Access 🔓 · `application/json`

| Body field | Type | Required | Rules |
| --- | --- | --- | --- |
| `email` | string (email) | ✅ | → `Invalid email address` |
| `password` | string | ✅ | same five password rules as register |

Email trimmed + lowercased; `bcrypt.compare`.

```
200 { "success": true, "statusCode": 200, "message": "User logged in successfully",
     "data": { "accessToken": "…", "refreshToken": "…" } }
```

+ both cookies (same options as above).

Errors: `400` validation · `404` `User not found` · `500` `User is blocked` · `500` `User is deleted` · `500` `Invalid credentials` (includes Google-only accounts, whose `password` is `null`).

#### `POST /auth/google`

Access 🔓 · `application/json` · **no Zod validation**

| Body field | Type | Required |
| --- | --- | --- |
| `idToken` | string — Google ID token | ✅ |

Verifies the token against `GOOGLE_CLIENT_ID`, then looks the account up by email: an existing account gets `googleId` linked (email must be verified; blocked/deleted rejected) and is signed in with its current role, otherwise a new `RECEIVER` user is created (`googleId` set, `emailVerified: true`, nested `customer`).

```
200 { "success": true, "statusCode": 200, "message": "New tokens generated successfully",
     "data": { "accessToken": "…", "refreshToken": "…" } }
```

+ both cookies.

Errors (all `AppError`, real status): `401` `Invalid Or Expired Google Id Token` · `400` `Google Email Not Found` · `400` `Google Email User Name Not Found` · `403` `Email Not Verified` · `403` `User Is Blocked` · `403` `User Is Deleted` · `404` `User Not Found`.

#### `POST /auth/forgot-password`

Access 🔓 · `application/json`

| Body field | Type | Required |
| --- | --- | --- |
| `email` | string (email) | ✅ → `Invalid email address` |

Stores Redis key `forgot-password-otp:<email>` (TTL 300 s) and emails the plain-text OTP.
⚠️ The email is **not** trimmed/lowercased here (unlike register/login) — casing must match `reset-password`.

```
200 { "success": true, "statusCode": 200, "message": "OTP sent to email <email>", "data": null }
```

Errors: `400` validation · `500` `user doesn't exists` · `500` `User not verified` · `500` `user is blocked` · `500` `user is deleted`.

#### `POST /auth/reset-password`

Access 🔓 · `application/json`

| Body field | Type | Required | Rules |
| --- | --- | --- | --- |
| `email` | string (email) | ✅ | → `Invalid email address` |
| `otp` | string, 6 chars | ✅ | → `Too small/Too big: expected string to have exactly 6 characters` |
| `newPassword` | string | ✅ | same five password rules as register |

```
200 { "success": true, "statusCode": 200, "message": "Password Changed Successfully", "data": null }
```

Side effects: hashes the new password, updates `User.password`, deletes the OTP key, sends confirmation email. Existing JWTs are **not** revoked.

Errors: `400` validation · `500` `user doesn't exists` · `500` `User not verified` · `500` `user is blocked` · `500` `user is deleted` · `500` `invalid otp` · `500` `otp doesn't match`.

#### `POST /auth/refresh-token`

Access 🔓 · token read from the **`refreshToken` cookie only** (no body, no header support).

```
200 { "success": true, "statusCode": 200, "message": "New tokens generated successfully",
     "data": { "accessToken": "…", "refreshToken": "…" } }
```

Rotates both cookies. The old refresh token is not invalidated (stateless).

Errors: `500` `Refresh token is missing` · `500` `jwt expired` / `invalid signature` (development) or `Invalid refresh token` (production) · `404` `User is inactive or not found`.

### 4.3 User profile

Mounted at `/api/v1/users`.

#### `GET /users/me`

Access 🔒 · No params.

```
200 { "success": true, "statusCode": 200, "message": "User profile retrieved successfully",
     "data": { …UserProfile… } }
```

`provider` contains `id`, `businessName`, `businessType`, `address`, `city`, `phone`, `isVerified`; `customer` contains `id`, `contactNumber`.

Errors: `401` (auth middleware shapes) · `401` `Authentication required` · `404` `User not found` (missing or soft-deleted).

#### `PATCH /users/me`

Access 🔒 · **`multipart/form-data`** (or JSON without a file) · file field **`file`** (1 file, 5 MB, images only).

Middleware order: auth → multer → Cloudinary upload → Zod validation → controller, so a file is uploaded **before** body validation runs.

| Body field | Type | Required | Rules / exact message |
| --- | --- | --- | --- |
| `name` | string | ⬜ | 3–10 chars → `Name must be at least 3 characters long` / `Name must be at most 10 characters long` |
| `imageUrl` | `""` or valid URL (≤500) | ⬜ | → `imageUrl must be a valid URL` / `imageUrl is too long` |
| `imagePublicId` | string ≤500 | ⬜ | → `imagePublicId is too long` |
| `contactNumber` | string ≤30 | ⬜ | → `contactNumber is too long` |
| *(object refine)* | — | — | empty body / only unknown keys → `At least one field is required` |

```
200 { "success": true, "statusCode": 200, "message": "User profile updated successfully",
     "data": { …fresh UserProfile… } }
```

Side effects: uploaded file goes to the Cloudinary folder `rescue-bite`; server-set `imageUrl`/`imagePublicId` override client values; `name` is written to both `User` and `Customer` (when a `Customer` row exists).

Errors: `400` `Only image files (JPEG, PNG, WEBP, GIF, AVIF, SVG) are allowed` · `400` `File exceeds the maximum allowed size of 5MB` · `400` `Unexpected file field` / `Too many files` · `400` validation messages · `404` `User not found` · `502` `Cloudinary upload failed: <msg>`.

### 4.5 Food listings

Mounted at `/api/v1/food-listings` (alias `/api/v1/food-listing`).

#### `POST /food-listings`

Access 🏪 · **`multipart/form-data`** with file field **`files`** (≤5) **or** `application/json`.

Multer limits: 5 MB per file, max 5 files; allowed MIME types `image/jpeg`, `image/png`, `image/webp`, `image/gif`, `image/avif`, `image/svg+xml`. Files are uploaded to Cloudinary (folder `rescue-bite`) and their URLs are merged into `images` before validation.

| Body field | Type | Required | Exact message |
| --- | --- | --- | --- |
| `foodName` | string, 2–100 | ✅ | `Food name must be a string` / `Food name must be at least 2 characters long` / `Food name must be at most 100 characters long` |
| `description` | string, 5–500 | ✅ | `Description must be a string` / `…at least 5 characters long` / `…at most 500 characters long` |
| `category` | `FoodCategory` | ✅ | `A valid food category is required` |
| `quantity` | integer > 0 (coerced) | ✅ | `Quantity must be a number` / `Quantity must be a whole number` / `Quantity must be greater than zero` |
| `unit` | string | ✅ | `Unit must be a string` / `Unit is required` |
| `price` | number ≥ 0 (coerced) | ✅ | `Price must be a number` / `Price cannot be negative` |
| `pickupLocation` | string ≥3 | ✅ | `Pickup location must be a string` / `…at least 3 characters long` |
| `pickupStartTime` | date string | ✅ | `Pickup start time is required` |
| `pickupEndTime` | date string | ✅ | `Pickup end time is required` |
| `expiryTime` | date string | ✅ | `Expiry time is required` |
| `images` | string[] ≤5 (JSON string, single URL or array accepted) | ⬜ | `At most 5 images are allowed` / `Each image must be a string` / `Image URL cannot be empty` |
| `status` | `FoodStatus` | ⬜ | default `DRAFT` |

Object refinements: `Pickup end time must be after pickup start time`, `Expiry time must be at or after pickup end time`.

```
201 { "success": true, "statusCode": 201, "message": "Food listing created successfully",
     "data": { …FoodListing… } }
```

Errors: `400` validation · `404` `Provider profile not found. Please create a provider profile first` · `400` upload errors (see [§4.8](#48-file-uploads)) · `502` Cloudinary.

#### `GET /food-listings` — public

Access 🔓 · Query params (parsed manually, then Zod-validated):

| Param | Type | Default | Notes / exact message |
| --- | --- | --- | --- |
| `search` | string | — | trimmed; case-insensitive `contains` over `foodName`, `description`, `pickupLocation` |
| `status` | `FoodStatus` (case-insensitive) | — | → `A valid food status filter is required` |
| `category` | `FoodCategory` (case-insensitive) | — | → `A valid food category filter is required` |
| `minPrice` | number ≥ 0 | — | → `minPrice must be a non-negative number` |
| `maxPrice` | number ≥ 0 | — | → `maxPrice must be a non-negative number`, and `minPrice cannot be greater than maxPrice` |
| `sortBy` | `createdAt`\|`foodName`\|`category`\|`price`\|`pickupStartTime`\|`expiryTime` | `createdAt` | → `A valid sort field is required` |
| `sortOrder` | `asc`\|`desc` | `desc` | → `sortOrder must be either 'asc' or 'desc'` |

```
200 { "success": true, "statusCode": 200, "message": "Food listings retrieved successfully",
     "data": [ …FoodListing… ] }
```

No pagination and **no default status filter** — `DRAFT`, `EXPIRED` and `CANCELLED` listings are publicly returned as well.

#### `GET /food-listings/my`

Access 🏪 · No params. Returns every listing of the caller's provider profile, `createdAt` descending.

```
200 … "message": "Food listings retrieved successfully", "data": [ … ]
```

Errors: `404` `Provider profile not found. Please create a provider profile first`.

#### `GET /food-listings/:id` — public

Access 🔓 · `200` `"Food listing retrieved successfully"` with a single listing.
Errors: `404` `Food listing not found`.

#### `PATCH /food-listings/:id/status`

Access 🏪 · **JSON only** (no multipart) · body: `status` (required `FoodStatus`) → `A valid food status is required`.

Allowed transitions:

| From | To |
| --- | --- |
| `DRAFT` | `AVAILABLE` |
| `AVAILABLE` | `PARTIALLY_RESERVED`, `FULLY_RESERVED`, `CANCELLED`, `EXPIRED` |
| `PARTIALLY_RESERVED` | `FULLY_RESERVED`, `EXPIRED` |
| `FULLY_RESERVED` | `EXPIRED` |
| `EXPIRED`, `CANCELLED` | *(none)* |

```
200 { …, "message": "Food listing status updated successfully", "data": { …FoodListing… } }
```

Errors: `400` `Food listing is already in <STATUS> status` · `400` `Invalid food listing status transition: <from> -> <to>` · `403` `Forbidden: You do not have permission to update this food listing` · `404` `Food listing not found` / `Provider profile not found. …`.

#### `PATCH /food-listings/:id`

Access 🏪 · multipart (`files`) or JSON. Body = the same fields as create, **all optional** (same messages and refinements). **`status` is not accepted here** (stripped) — use `/status`.

```
200 { …, "message": "Food listing updated successfully", "data": { …FoodListing… } }
```

Rules: only listings in `DRAFT`, `AVAILABLE` or `PARTIALLY_RESERVED` are editable → otherwise `400` `Only DRAFT, AVAILABLE, PARTIALLY_RESERVED food listings can be updated`. Omitting `images` keeps existing images; sending `images: []` clears them. `403` on foreign listings, `404` when missing.

#### `DELETE /food-listings/:id`

Access 🏪 · Hard delete, any status.

```
200 { "success": true, "statusCode": 200, "message": "Food listing deleted successfully", "data": null }
```

Errors: `403` `Forbidden: You do not have permission to delete this food listing` · `404` `Food listing not found`.

### 4.6 Reservations

Mounted at `/api/v1/reservations` (alias `/api/v1/reservation`). All four require 👤.

#### `POST /reservations`

JSON only.

| Body field | Type | Required | Exact message |
| --- | --- | --- | --- |
| `listingId` | string | ✅ | `Listing id is required` |
| `quantity` | integer > 0 (**not** coerced — `"2"` fails) | ✅ | `Quantity must be a number` / `Quantity must be a whole number` / `Quantity must be greater than zero` |

Transaction steps: validate customer → validate listing → check status/expiry/stock → create `Reservation` (`RESERVED`) → flip listing to `PARTIALLY_RESERVED`/`FULLY_RESERVED` → create a `PENDING` payment (`tranId = reservationId`, `amount = price × quantity`) → **after commit**, initiate SSLCommerz checkout.

```
201 {
  "success": true, "statusCode": 201,
  "message": "Food reserved. Complete the payment to finalize",
  "data": {
    "id": "…", "listingId": "…", "customerId": "…", "quantity": 2, "status": "RESERVED",
    "foodName": "…", "category": "GROCERY", "pickupLocation": "…",
    "pickupStartTime": "…", "pickupEndTime": "…", "expiryTime": "…",
    "cancelledAt": null, "completedAt": null, "createdAt": "…", "updatedAt": "…",
    "payment": { "id": "…", "tranId": "…", "amount": 240, "status": "PENDING",
                 "gatewayPageURL": "https://sandbox-gw.sslcommerz.com/…" }
  }
}
```

**`data.payment.gatewayPageURL` is the hosted checkout URL the client must redirect the user to.**

Errors: `404` `Customer profile not found. Please register as a receiver first` · `404` `Food listing not found` · `400` `Food listing is not available for reservation` (status must be `AVAILABLE` or `PARTIALLY_RESERVED`) · `400` `Food listing has already expired` · `400` `Only <n> unit(s) are available for reservation` · `502` `SSLCommerz initiation failed: <reason>` (reservation + pending payment remain created).

#### `GET /reservations/my`

No params. `200` `"Reservations retrieved successfully"`, `data` = `Reservation[]` ordered `createdAt` desc (no `payment` object).

#### `GET /reservations/:id`

`200` `"Reservation retrieved successfully"`.
Errors: `400` `Invalid reservation id` · `404` `Reservation not found` · `403` `Forbidden: You do not have permission to view this reservation`.

#### `PATCH /reservations/:id/cancel`

No body. Inside a transaction: marks `CANCELLED` + `cancelledAt = now`, then re-computes listing stock (`deallocateListing`) so the listing returns to `AVAILABLE`/`PARTIALLY_RESERVED`.

```
200 { …, "message": "Reservation cancelled successfully", "data": { …Reservation, status: "CANCELLED" } }
```

Errors: `404` `Reservation not found` · `403` `Forbidden: You do not have permission to cancel this reservation` · `400` `Only eligible (active) reservations can be cancelled` · `400` `Reservation can no longer be cancelled because the listing is no longer active`.

### 4.7 Payments

Mounted at `/api/v1/payments`. Gateway: **SSLCommerz** (sandbox in `.env`).

#### `GET /payments/my`

Access 👤 · No params.

```
200 { …, "message": "Payments retrieved successfully",
      "data": [ { "id": "…", "reservationId": "…", "amount": 240, "status": "SUCCESS",
                  "tranId": "…", "createdAt": "…", "updatedAt": "…",
                  "reservation": { "id": "…", "quantity": 2, "status": "RESERVED",
                                   "foodName": "…", "pickupLocation": "…" } } ] }
```

`gatewayData` is excluded. Errors: `404` `Customer profile not found. Please register as a receiver first`.

#### Gateway callbacks — `GET|POST /payments/success`, `/fail`, `/cancel`, `/ipn`

All are 🔓 and read `{ ...req.query, ...req.body }` (body wins on collision), so both GET redirects and POST form posts work.

| Param | Meaning |
| --- | --- |
| `tran_id` | transaction id (equals the reservation id) — **required** |
| `val_id` | SSLCommerz validation id — required for real settlements |
| `amount`, `currency`, `status`, `card_type`, `bank_tran_id` | stored in `gatewayData` |

**`/success`** — with `val_id`, calls the SSLCommerz validation API server-side; settles `SUCCESS` when `status` is `VALID`/`VALIDATED` and `tran_id`/`amount` match (0.01 tolerance), otherwise `FAILED`. Without `val_id` it only acknowledges and waits for the IPN.

**`/fail`**, **`/cancel`** — settle the payment as `FAILED` / `CANCELLED` with no gateway call.

**Settlement rules (shared):**
- already `SUCCESS` → idempotent no-op;
- already `FAILED`/`CANCELLED` → `409 Payment already settled as <STATUS>` (surfaced as a redirect `?error=…` for browser callbacks);
- `SUCCESS` updates only the payment (the reservation stays `RESERVED`);
- `FAILED`/`CANCELLED` also set the reservation to `CANCELLED` (+`cancelledAt`) and recompute listing stock.

**Browser callbacks answer with `302`, never JSON:**

| Endpoint | Redirect |
| --- | --- |
| `/success` | `<FRONTEND_URL>/payment/success?tran_id=<tranId>&status=<PaymentStatus>` |
| `/fail` | `<FRONTEND_URL>/payment/fail?tran_id=<tranId>&status=FAILED` |
| `/cancel` | `<FRONTEND_URL>/payment/cancel?tran_id=<tranId>&status=CANCELLED` |
| any error | `<FRONTEND_URL>/payment/<success\|fail\|cancel>?error=<message>` |

`FRONTEND_URL` falls back to `https://rescuebite-frontend.onrender.com` when unset. Errors that trigger a redirect: `400 tran_id is required`, `404 Payment not found for tran_id <id>`, validation mismatches.

**`POST/GET /payments/ipn`** — returns JSON:

```
200 { "success": true, "statusCode": 200, "message": "IPN processed successfully",
      "data": { "payment": { … }, "reservationStatus": "RESERVED" } }
```

Errors: `400 tran_id is required` · `404 Payment not found for tran_id <id>` · `409 Payment already settled as <STATUS>`.
Missing `val_id` on IPN settles the payment as `FAILED` with `gatewayData.reason = "val_id missing on IPN callback"`.

## 8. Known limitations

Documented here so client authors can code around them:

1. **Several auth/validation failures return HTTP 500** instead of 4xx (see [§5](#5-error-reference)) — branch on `message`, not only on status.
2. **Auth middleware responses** use `{success,message}` while everything else uses the full envelope — handle both shapes.
3. **Only the admin list endpoints paginate.** `GET /food-listings`, `GET /reservations/my` and `GET /payments/my` return unbounded arrays.
4. **No scheduled jobs.** `FoodStatus.EXPIRED` is only ever set manually via `PATCH /:id/status`; expiry is otherwise checked on read/reservation (`Food listing has already expired`).
5. **No rate limiting / CSRF protection / request logging**; CORS is configured as `cors({ credentials: true })` with no explicit origin (effectively `*`), so the web client sends tokens in the `Authorization` header with `credentials: "omit"`.
6. **OTP flows are single-use with a 5-minute TTL** and are stored in Redis (`customer registration otp: <email>`, `customer-registration-data:<email>`, `forgot-password-otp:<email>`).
7. **`password` is never returned**, but error messages reveal account state (existence, verification, block status).
8. **`GET /test` never responds** and `POST /zod` is a scratch endpoint — neither is part of the public contract.
9. Replacing a profile image does not delete the previous Cloudinary asset.
10. `reset-password` does not revoke previously issued JWTs.
